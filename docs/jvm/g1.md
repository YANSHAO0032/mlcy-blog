# G1 垃圾收集器：从 Region 到低停顿调优

G1（Garbage-First Garbage Collector）是 JDK 21 服务端应用中常见的低停顿收集器。它的关键思想不是把整个堆一次性扫描完，而是把堆划分成许多大小相等的 Region，优先回收收益更高的 Region，并在暂停预算内逐步完成整理。

这篇文章结合工程的订单服务、RocketMQ 消费和 WebSocket 推送场景，解释 G1 如何工作、哪些参数值得关注，以及如何用指标判断调优是否真的有效。文中的 JVM 参数是 JDK 21 的评估模板，不代表 `ex-parent` 当前已经提交了同样的启动参数。

## 1. 内存特征

运行形态包含普通 API、订单处理、RocketMQ 消费和独立的 WebSocket 推送服务。源码中可以看到几类与 GC 直接相关的对象来源：

- 订单请求、撮合结果和消息体在序列化、反序列化过程中产生大量短命对象。
- 订单消费者和推送消费者使用线程池并发处理任务，排队任务会延长对象的存活时间。
- WebSocket 推送服务维护连接、订阅关系和心跳状态，连接映射属于相对长寿命对象。
- 本地缓存、批量查询结果和消息批次可能形成大集合，甚至产生 Humongous Object。

因此不能只问“G1 停顿多久”，还要问：对象分配速度是多少、消息积压是否让对象活得更久、推送连接和订阅映射是否持续增长。

## 2. G1 解决什么问题

传统分代收集器通常把堆抽象为 Eden、Survivor 和 Old 区，再按照整块空间执行回收。G1 仍然保留对象年龄和分代回收的思想，但物理上把整个 Java Heap 划成大量 Region。每个 Region 在不同阶段可以承担 Eden、Survivor 或 Old 的角色。

G1 的目标是同时兼顾：

- 面向较大堆的可扩展性
- 对停顿时间的可预测控制
- 回收后整理空间，降低碎片风险
- 通过 Mixed GC 增量回收一部分老年代

G1 不是“没有停顿”，也不是“停顿目标越低越好”。它是在分配压力、CPU 预算和回收收益之间做动态取舍。

## 3. Region 如何组织堆

G1 将堆划分为多个大小一致的 Region。Region 大小由 JVM 根据堆大小选择，也可以用 `-XX:G1HeapRegionSize` 设置，取值通常是 1 MB 到 32 MB 之间的 2 的幂。

逻辑角色主要包括：

| Region 角色 | 作用 |
| --- | --- |
| Eden Region | 分配新对象的主要区域 |
| Survivor Region | Young GC 后保存仍然存活的对象 |
| Old Region | 保存年龄较高或不适合继续留在年轻代的对象 |
| Humongous Region | 保存超过 Region 一半的大对象，通常需要连续的 Region |
| Free Region | 等待后续分配或回收使用 |

对象不要求永远停留在某个固定代中。一次 Young GC 后，Eden Region 被回收，存活对象复制到 Survivor Region 或 Old Region；老年代 Region 则由后续的并发标记和 Mixed GC 逐步选择回收。

### 3.1 为什么要关注 Humongous Object

大对象通常是一次性生成的批量结果、很大的 JSON、图片/文件内容或异常膨胀的集合。它们可能占用多个连续 Region，回收和分配都比普通对象更敏感。

在 `ex-parent` 这类订单和推送系统中，需要特别检查：

- 是否一次性把大量订单或行情数据拼成一个消息
- 是否把大批量查询结果完整保存在内存中
- 是否使用了过大的序列化缓冲区
- 是否存在异常消息导致单条对象尺寸远超正常分布

盲目增大堆只能延后问题，不能改变大对象的分配模型。

## 4. G1 的一次回收如何发生

### 4.1 Young GC

当 Eden Region 不足以承载新的分配时，G1 触发 Young GC。典型过程是：

```text
Eden Region 分配
-> Young GC
-> 存活对象复制到 Survivor 或 Old Region
-> Eden Region 释放并重新加入 Free Region
```

Young GC 通常需要 Stop-The-World，因为对象复制、引用更新和部分根扫描需要在一致状态下完成。Young GC 次数多并不自动意味着故障，真正要看的是单次停顿、分配速率和回收后堆水位。

### 4.2 并发标记周期

当老年代占比达到启动阈值后，G1 会启动并发标记周期，识别哪些老年代 Region 中仍有多少存活对象。典型阶段可以简化为：

```text
Initial Mark
-> Concurrent Mark
-> Remark
-> Cleanup
```

`Initial Mark` 通常借助一次 Young GC 完成根集合初始标记；`Concurrent Mark` 与业务线程并发执行；`Remark` 修正并发期间发生变化的引用；`Cleanup` 统计 Region 的回收收益并为后续 Mixed GC 提供依据。

### 4.3 Mixed GC

Mixed GC 不只回收年轻代，还会挑选部分垃圾比例较高的 Old Region 一起回收。G1 的“Garbage-First”就体现在这里：在暂停预算允许的情况下，优先选择回收收益较高的 Region。

Mixed GC 的收益取决于并发标记是否及时、老年代垃圾比例是否足够高，以及回收阶段是否有足够的 CPU 和复制空间。如果业务分配速度很高，并发标记跟不上，G1 可能退化为更重的 Full GC。

## 5. Remembered Set 和写屏障

G1 不可能在每次 Young GC 时扫描整个堆来寻找跨 Region 引用，因此需要维护 Remembered Set（简称 RSet）。RSet 记录“哪些 Region 可能有指向当前 Region 的引用”，让 GC 可以缩小扫描范围。

对象引用发生变化时，写屏障会把相关卡表信息记录下来，后台线程再处理这些记录。代价是：

- 业务写引用时增加少量 CPU 开销
- RSet 占用额外内存
- 跨 Region 引用很多时，GC 工作量可能上升

这解释了为什么 G1 的吞吐不一定优于追求吞吐的收集器。低停顿能力来自额外的并发工作、写屏障和空间管理，而不是没有成本。

## 6. `MaxGCPauseMillis` 到底意味着什么

常见配置如下：

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
```

`MaxGCPauseMillis` 是 G1 的停顿目标，不是每次 GC 都必须小于 200 毫秒的硬性承诺。G1 会根据目标调整年轻代大小和回收集合，但以下因素仍然可能让停顿超标：

- 单位时间分配速率过高
- 存活对象太多，复制成本过大
- Region 中跨代引用和 RSet 处理量过大
- CPU 配额不足或 GC 线程被限流
- Humongous Object 分配造成额外压力
- 并发标记没有及时完成

把目标从 200 毫秒直接降到 20 毫秒，通常会让每次暂停工作量变少，但也可能导致更频繁的 GC、更多并发开销和更低吞吐。目标应该结合 API P99、订单处理延迟和 CPU 使用率一起设定。

## 7. JDK 21 的评估配置模板

下面是一组适合压测起步的 G1 模板：

```bash
java \
  -Xms4g -Xmx4g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=100 \
  -Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=100M \
  -jar exchange-app-api.jar
```

说明：

- `-Xms` 与 `-Xmx` 固定为相同值，减少运行中堆扩缩容带来的变量。
- `MaxGCPauseMillis` 只是初始目标，应以压测结果校准。
- JDK 21 使用统一日志框架 `-Xlog`，不要把旧格式日志参数当作默认方案。
- 容器内存预算不能只等于 Java Heap，还要为 Metaspace、线程栈、Direct Buffer、JIT Code Cache 和 native library 预留空间。

建议先用一组固定堆大小运行基线，再逐步改变堆大小、暂停目标和 CPU 配额，每次只改变一个主要变量。

## 8. 重点观察哪些指标

### GC 指标

- Young GC 次数、平均停顿和 P99 停顿
- Mixed GC 次数和单次回收 Region 数量
- Full GC 次数、触发原因和停顿时间
- 并发标记周期是否频繁中断或未及时完成
- Eden、Survivor、Old 和 Humongous Region 的占用趋势
- GC 时间占进程运行时间的比例

### 业务指标

- 订单 API P99/P999 延迟
- MQ 消费吞吐、消费积压和单条消息处理耗时
- WebSocket 连接数、订阅映射大小和推送队列长度
- 线程池活动线程、队列长度和拒绝次数
- 容器 CPU、内存 RSS 和重启情况

最有价值的判断不是“GC 次数少了”，而是 GC 停顿尖刺是否和业务延迟尖刺同时下降，并且消费吞吐没有明显回退。

## 9. 结合工程的调优场景

### 9.1 订单服务：短命对象和突发分配

订单请求、校验、数据库映射和消息构造会产生大量临时对象。如果 Young GC 很频繁但每次停顿很短，首先看单位时间分配速率和序列化代码，而不是立即把堆调大。

如果订单处理变慢导致线程池排队，排队中的请求对象会活得更久，进而增加 Survivor 压力和老年代晋升。此时要同时观察线程池队列、数据库耗时和 Old Region 趋势。

### 9.2 RocketMQ 消费：积压让对象生命周期变长

消费者从 RocketMQ 拉取消息后，消息批次、反序列化对象和业务中间结果会在处理期间存活。如果消费速度下降，积压本身不一定直接占用 JVM 堆，但批量拉取、重试队列和未完成任务会延长对象生命周期。

排查时要关联消费 TPS、批量大小、线程池队列和 GC 后 Old 区占用，避免把消息积压简单归因于 G1 参数。

### 9.3 WebSocket 推送：长寿命连接和短命消息并存

WebSocket 服务同时存在两类对象：连接、订阅映射、认证信息等长寿命对象，以及行情/成交消息、JSON 文本和发送缓冲等短命对象。

如果连接数稳定但推送队列持续增加，GC 可能只是结果，不是根因。应先限制队列长度、处理慢客户端和检查订阅映射清理，再看 G1 是否因分配速率下降而恢复。

## 10. 常见失败模式

| 现象 | 优先验证 | 可能动作 |
| --- | --- | --- |
| Young GC 很多，停顿很短 | 分配速率、对象临时性 | 优先优化序列化、批量大小和无效对象 |
| Mixed GC 跟不上 | 并发标记周期、Old 趋势、CPU | 调整堆余量和暂停目标，检查分配尖峰 |
| Full GC 频繁 | 触发原因、Humongous Object、堆外压力 | 处理大对象和泄漏，确认容器内存预算 |
| Full GC 后 Old 仍高 | Heap dump、缓存和引用链 | 修复对象持有，不要只调收集器参数 |
| GC 与 RT 一起抖高 | GC 日志、CPU throttling、线程池 | 对齐时间线，排除容器和下游依赖 |

## 11. G1 调优检查清单

1. 确认进程确实使用 JDK 21 和 G1。
2. 固定堆大小，打开统一 GC 日志和 safepoint 日志。
3. 同时采集 GC P99、业务 P99、CPU、RSS、线程池和 MQ 指标。
4. 分清短命对象、晋升对象、Humongous Object 和长寿命缓存。
5. 每轮只改变一个主要变量，并用相同流量重放。
6. 以业务延迟、吞吐和稳定性评价结果，不以 GC 次数单独评价。

## 总结

G1 的价值是把大堆回收拆成可控制的 Region 集合，并通过并发标记和 Mixed GC 在停顿预算内逐步回收。对工程而言，真正需要调优的往往不是某一个参数，而是订单分配速率、MQ 消费积压、WebSocket 长连接和线程池排队共同形成的对象生命周期。只有把 GC 日志和业务指标放在同一条时间线上，G1 的参数调整才有意义。
