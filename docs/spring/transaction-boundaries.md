# Spring 事务边界设计：事务不是注解，而是数据一致性的表达

## Problem

很多项目里 `@Transactional` 用得很勤，但问题也很多：

- 明明加了事务，为什么还是回滚失败？
- 为什么同类方法互调时事务不生效？
- 为什么一个大事务把数据库拖慢了？
- 为什么消息发送、缓存更新、数据库写入放在一个事务里还是不一致？

这些问题说明，事务真正难的地方从来不是会不会写注解，而是会不会划边界。

## Explanation

我更愿意把 Spring 事务理解成一套“一致性边界表达工具”，而不是一个自动兜底开关。

### 1. 事务的核心不是回滚，而是边界

一个事务最重要的问题不是“会不会提交”，而是：

- 哪些操作必须一起成功或失败
- 哪些操作可以异步补偿
- 哪些状态应该落库，哪些状态只该放缓存

如果这个边界没想清楚，`@Transactional` 写得再多也只是表面稳定。

### 2. Spring 事务基于 AOP 代理，不是语言级能力

这意味着两个关键事实：

- 只有经过代理对象的方法调用，事务拦截器才会生效
- 同类内部 `this.method()` 调用，通常不会触发事务切面

这也是常见事务失效的根源之一。

所以我通常会提醒自己：

```text
事务不是加在方法上就自动生效，而是加在“通过代理进入的方法边界”上才生效。
```

### 3. 大事务往往是性能和锁争用问题的源头

比如一个现货系统里的下单流程，如果把下面这些动作全塞进一个事务：

- 订单落库
- 账户冻结
- 操作日志
- 消息发送
- Redis 更新
- 风控记录

那这个事务一旦慢下来，就会把锁持有时间、连接占用时间和失败影响面一起放大。

更合理的做法通常是：

- 把数据库内必须强一致的动作收敛成核心事务
- 把通知、统计、缓存刷新、报表同步拆成事务后事件

### 4. 事务传播行为体现的是“嵌套边界如何协作”

常见传播行为里，我最常用的是：

- `REQUIRED`
- `REQUIRES_NEW`
- `NOT_SUPPORTED`

理解重点不是背定义，而是知道它们在表达什么：

- `REQUIRED`：当前逻辑属于主事务的一部分
- `REQUIRES_NEW`：这段逻辑要独立成自己的提交单元
- `NOT_SUPPORTED`：这段逻辑不应该绑在数据库事务里

例如审计日志、补偿记录、失败落盘，有时更适合 `REQUIRES_NEW`，因为你希望它即使主事务失败也能保留排查线索。

### 5. 事务解决不了跨系统一致性

这是业务工程里最容易被高估的一点。

Spring 事务主要解决的是单库或本地资源边界内的一致性，它解决不了：

- 数据库和 Kafka 的天然原子一致
- 数据库和 Redis 的天然一致
- 数据库和第三方 RPC 的天然一致

这类问题更适合：

- 本地消息表
- 事务后事件
- Outbox 模式
- 幂等消费
- 补偿机制

### 6. 在交易和资金系统里，事务应该越核心越小

一个比较稳的原则是：

```text
越靠近资金、订单、库存这类核心状态，事务越应该小、清晰、可审计。
```

因为核心事务的目标不是“包住一切”，而是“把不可分割的状态变化锁在最小边界里”。

## Key Points

- `@Transactional` 本质上是在表达一致性边界。
- Spring 事务依赖代理调用，同类内部调用常常会失效。
- 大事务会放大锁争用、连接占用和失败影响面。
- 传播行为的重点是边界协作，不是定义背诵。
- 跨系统一致性不能只靠本地事务，要结合事件和补偿设计。

## Summary

Spring 事务真正的价值，不是帮你“自动回滚”，而是让你把数据一致性的边界表达清楚。把事务当成架构边界工具，而不是注解习惯，系统会稳很多，排障也会清晰很多。
