# Spring 事件驱动实践：解耦不是把方法改成异步，而是重建协作边界

## Problem

很多项目到后期都会出现这种情况：

- 下单成功后要同步改十几个模块
- 一个运营动作会牵出返佣、消息、统计、审计、推送
- Service 越写越长，谁依赖谁越来越不清楚

这时很多团队会想到“用事件驱动”。但如果只是把同步调用改成 `@Async`，问题通常并没有真正解决。

## Explanation

我理解 Spring 里的事件驱动，重点不是“发个事件”，而是把主链路和旁路能力重新切边界。

### 1. 事件驱动最适合处理“结果已确定后的旁路协作”

最适合事件化的场景通常是：

- 订单创建后的通知
- 成交结果后的统计
- 返佣结算触发
- 审计日志记录
- 缓存刷新

这些逻辑有一个共同点：

- 主结果已经产生
- 旁路逻辑依赖主结果
- 旁路失败不一定要阻塞主流程

这时候用事件驱动最合适。

### 2. Spring 事件适合站内解耦，不适合代替消息队列

Spring 自带的 `ApplicationEventPublisher` 很轻量，适合做：

- 单体应用内模块解耦
- 启动事件、领域事件广播
- 本地事务后的监听扩展

但它不是消息中间件，不适合直接承担：

- 跨进程可靠投递
- 大规模堆积消费
- 重试补偿队列
- 持久化事件流

所以我的原则通常是：

- 站内解耦优先用 Spring 事件
- 跨系统传播优先用 Kafka / MQ

### 3. 先区分“领域事件”和“技术事件”

这是我觉得很容易体现理解深度的一点。

领域事件描述业务结果，例如：

- `OrderCreatedEvent`
- `TradeMatchedEvent`
- `RebateSettledEvent`

技术事件描述系统动作，例如：

- 缓存刷新
- 指标上报
- 日志归档

如果两者混在一起，事件总线会很快失控。把它们分开，模块边界会清楚很多。

### 4. 事务后事件比“事务里顺手做完”更稳

很多旁路动作不应该写在主事务里，比如：

- 发送通知
- 推送 WebSocket
- 统计报表更新
- 代理返佣触发

更合理的方式通常是：

- 主事务只处理核心状态
- 事务提交成功后发布事件
- 监听器做幂等处理和旁路扩展

这套模式在交易和增长场景里尤其重要，因为主链路追求的是稳定和低延迟，不适合被旁路逻辑拖住。

### 5. 事件驱动的最大风险不是复杂，而是失控

常见问题包括：

- 谁发布了事件没人知道
- 谁消费了事件没人知道
- 事件字段不断膨胀
- 监听器之间隐式依赖
- 失败重试没有统一策略

所以我更倾向于给事件体系加约束：

- 事件名有业务语义
- 事件 payload 尽量稳定
- 监听器职责单一
- 幂等键明确
- 失败路径可追踪

### 6. 在增长系统里，事件驱动特别有价值

比如一个用户成交后，可能触发：

- 返佣结算
- 活动进度更新
- 用户等级判断
- 统计报表聚合
- 站内消息推送

如果这些全同步串在交易链路里，主流程会越来越重。拆成事件驱动后，主链路和增长链路的职责会清晰很多。

## Key Points

- Spring 事件驱动的核心是重建协作边界，不是简单异步化。
- Spring 事件适合站内解耦，Kafka / MQ 更适合跨系统传播。
- 要区分领域事件和技术事件。
- 核心事务外的旁路逻辑更适合用事务后事件承接。
- 事件体系必须有命名、幂等、失败追踪和监听器边界约束。

## Summary

Spring 事件驱动真正有价值的地方，不是“让代码看起来高级”，而是把主链路和旁路能力切开。对复杂业务系统来说，这比把所有逻辑塞进一个 Service 里更稳定，也更像成熟工程团队的做法。
