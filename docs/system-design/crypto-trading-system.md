# Crypto 交易系统整体架构设计：不是订单系统放大版，而是一套低延迟与强一致并存的基础设施

## Problem

很多人理解交易系统时，容易把它看成“高并发版订单系统”。但真正进入现货交易场景后，会很快发现它和普通业务系统有本质差异：

- 下单链路追求低延迟，不能被旁路逻辑拖慢
- 撮合结果会持续驱动账户、行情、风控和增长系统
- 资产变动必须可审计、可回放、可补偿
- 一旦订单状态和资金状态不一致，问题就不是“功能异常”，而是资损风险

所以交易系统真正难的，不是多几个服务，而是如何同时满足：

- 交易链路快
- 资金链路稳
- 事件链路清晰
- 故障恢复可控

## Explanation

我理解一套成熟的 crypto 现货交易系统，核心不是“服务拆得多细”，而是有没有把不同目标的链路切清楚。

比较合理的架构，一般会拆成下面几个层次：

```text
接入层
-> 订单编排层
-> 撮合执行层
-> 资金账户层
-> 行情与事件分发层
-> 风控与运营协同层
-> 审计、对账与恢复层
```

### 1. 接入层：负责接住请求，而不是承载全部业务

接入层通常包括：

- API 网关
- 下单 / 撤单接口
- 用户权限校验
- 限流和幂等键透传
- traceId / requestId 管理

这一层最重要的目标不是算业务，而是把请求变成一条可验证、可跟踪、可拒绝的标准输入。

也就是说，接入层应该回答的是：

- 这个请求是否合法
- 这个用户有没有资格下这个单
- 这是不是一次重复请求
- 这条请求后续如何被追踪

### 2. 订单编排层：连接业务规则和撮合能力

订单编排层不是撮合引擎本身，而是下单前后的业务边界控制层。它通常负责：

- 参数标准化
- 交易对状态检查
- 价格精度、数量精度校验
- 用户交易权限和风控阈值检查
- 资产可用性预校验
- 下单结果与内部订单状态同步

我对这一层的理解是：

```text
它不负责决定谁和谁成交，
但它负责决定“什么样的订单可以安全地进入撮合世界”。
```

### 3. 撮合执行层：目标是确定性和低延迟

撮合引擎最重要的不是“会不会写红黑树或 SkipList”，而是：

- 输入顺序是否确定
- 同样输入是否能产生同样输出
- 高并发下是否还能保持低延迟
- 故障后是否能回放恢复

在 matching-engine 这类架构里，比较重要的设计思想包括：

- 单线程 Actor 模型减少共享状态竞争
- 订单簿状态驻留内存，避免频繁数据库参与主撮合
- 事件流输出标准化成交结果
- 支持快照 + replay 恢复

所以撮合层的职责很明确：

- 接收合法订单事件
- 产生确定性的撮合结果
- 不直接承担复杂的资金、增长、报表逻辑

### 4. 资金账户层：从交易结果到资金结果的唯一可信执行者

一笔成交对系统来说，不算“完成”，直到它变成了明确的资金变更。

资金账户层通常负责：

- 冻结下单所需资产
- 成交后扣减冻结余额
- 给对手方入账
- 扣手续费
- 撤单解冻剩余资产
- 落资金流水和审计记录

这层和撮合层的目标完全不同：

- 撮合层追求低延迟和确定性
- 资金层追求幂等、一致性和审计可追踪

所以我更倾向于把它们看成两种完全不同的系统目标，而不是一个大事务里的两个步骤。

### 5. 行情与事件分发层：把成交结果变成“可消费的基础事实”

撮合结果出来后，不是只有订单状态要变。还会有很多下游系统依赖：

- 行情快照
- 深度增量
- K 线统计
- 用户成交推送
- 风控统计
- 增长返佣结算

因此，一个成熟系统必须把成交结果标准化成事件流，而不是靠各服务自己去读库拼状态。

这一层通常要做的是：

- 统一事件模型
- 按交易对或业务域拆分主题
- 支持增量广播和快照恢复
- 给下游消费提供幂等依据

### 6. 风控与运营协同层：依赖交易结果，但不侵入主交易链路

这是很多系统最容易做重的地方。

风控、增长、活动、返佣、报表都很重要，但它们不应该阻塞主交易链路。更合理的做法通常是：

- 主交易链路只输出标准结果
- 旁路系统消费结果事件
- 旁路失败可重试、可补偿、可审计

如果把返佣、消息通知、报表统计都同步塞进下单事务里，最终一定会把主链路拖垮。

### 7. 审计、对账与恢复层：这是交易系统专业度最容易被忽视的一层

真正做过交易系统的人，通常不会只谈下单和撮合，还会特别重视：

- 订单和成交能不能重建
- 资金流水能不能对账
- 事件流能不能回放
- 快照和日志能不能恢复服务
- 异常单据能不能补偿和人工介入

因为线上系统真正拉开差距的，不是“平时能不能跑”，而是“出问题时能不能看懂、修复并恢复”。

## 设计重点

### 主链路和旁路链路必须分层

我比较坚持的一条原则是：

```text
下单、撮合、资金是主链路；
报表、返佣、通知、运营统计是旁路链路。
```

旁路逻辑再重要，也不应该直接侵入主链路的一致性边界。

### 订单状态和资金状态要分别建模

订单系统不应该假设“成交了就等于资金一定处理完”，资金系统也不应该假设“有资金流水就说明订单状态已经同步完”。

更成熟的做法是：

- 订单有自己的状态机
- 资金有自己的状态机
- 两者通过事件和幂等键关联

这样出问题时，才能分清到底是撮合没出结果、订单没推进，还是资金没落账。

### 事件要可审计，不要只做“消息通知”

很多系统会把事件总线用成“异步回调工具”，但交易系统里的事件应该更像“基础事实流”：

- 有稳定事件类型
- 有唯一业务键
- 有顺序或分区语义
- 可以被重放
- 可以做审计和对账

### 故障恢复能力要提前设计，不要事后补

如果撮合进程挂掉、行情服务落后、账户服务短暂异常，一个成熟系统要能回答：

- 怎么恢复到正确状态
- 哪些结果要重放
- 哪些事件要补偿
- 哪些用户状态可能受影响

这部分如果没有提前设计，系统一旦复杂起来，后面几乎补不回来。

## Key Points

- 交易系统不是订单系统放大版，而是低延迟、强一致、强审计并存的基础设施。
- 接入、订单编排、撮合、资金、行情、旁路系统要明确分层。
- 撮合链路追求确定性和低延迟，资金链路追求幂等和可审计。
- 主链路与旁路链路必须解耦，避免把增长、报表、通知塞进核心事务。
- 真正成熟的交易系统，一定重视事件流、对账、回放和恢复能力。

## Summary

Crypto 交易系统真正的专业度，不在于“服务有多少”，而在于有没有把交易速度、资金一致性、事件治理和故障恢复这些目标同时组织起来。交易链路要快，资金链路要稳，事件链路要清晰，恢复链路要可控。把这四件事同时做好，才是一套像样的交易系统架构。
