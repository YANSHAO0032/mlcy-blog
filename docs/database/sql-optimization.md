# SQL 优化实践：慢 SQL 的问题通常不在 SQL 语法，而在访问路径

## Problem

为什么同样是 CRUD，有的 SQL 可以稳定跑几十毫秒，有的却会慢到秒级？为什么“业务逻辑没改多少”，数据库压力却突然上来了？

## Explanation

我理解 SQL 优化，关键不是把语句写得多漂亮，而是优化它的访问路径。

一个 SQL 真正的成本，通常来自：

- 扫描了多少行
- 是否走对了索引
- 是否发生大量回表
- 是否排序 / 分组无法在索引层完成
- 是否产生临时表和 filesort

所以 SQL 优化，本质上是在想办法让数据库：

- 少扫
- 少回表
- 少排序
- 少做无效计算

### 1. 优化 SQL 的第一步，不是拍脑袋改写

我通常先看：

- 这条 SQL 的执行频率
- 平均耗时和 P99 耗时
- 扫描行数
- 返回行数
- 执行计划

有些 SQL 看起来“写得不优雅”，但频率低、耗时稳定，未必值得优先优化。

真正值得下手的，通常是：

- 高频慢查询
- 影响主链路的查询
- 容易引发连接堆积的后台查询

### 2. 大多数慢 SQL，都有典型模式

#### 2.1 没走索引或索引利用率差

常见表现：

- `type=ALL`
- 扫描行数巨大
- CPU 高但结果返回不多

#### 2.2 深分页

```sql
limit 100000, 20
```

这种 SQL 即使有索引，也可能因为要跳过大量数据而变慢。

#### 2.3 排序 / 分组没命中索引

常见表现：

- `Using filesort`
- `Using temporary`

#### 2.4 回表太多

特别是在列表场景里，条件过滤后命中了很多行，再回表取大字段，成本会迅速放大。

### 3. SQL 优化常见动作

#### 缩小返回列

`select *` 往往不是好习惯，特别是：

- 表列很多
- 有大字段
- 列表页只需要少数字段

#### 改写过滤条件

避免：

- 对索引列做函数
- 隐式类型转换
- 前置 `%like`

#### 调整索引

比起“加单列索引”，很多时候更需要的是：

- 联合索引
- 覆盖索引
- 与排序方向匹配的索引

#### 改写分页模式

能用游标翻页时，尽量少用深 offset。

### 4. SQL 优化不能只看单条语句，还要看系统上下文

有时慢 SQL 不只是 SQL 自己慢，而是：

- 连接池被打满
- 大事务拖住了锁
- 批任务和在线查询争资源
- 热点索引页竞争

所以优化时不能只盯着 SQL 文本，还要看它在系统中的位置。

### 5. 对后端工程师来说，最重要的是形成“访问路径思维”

我更看重的不是“记住几条优化口诀”，而是看到一条 SQL 时能立刻想到：

- 它会先走哪棵索引树
- 预计扫描多少行
- 会不会回表
- 排序在哪完成
- 是否会和热点写入冲突

这种访问路径思维，才是数据库优化真正有价值的部分。

## Key Points

- 慢 SQL 的核心问题通常是访问路径差，而不是语法不优雅。
- 重点看扫描行数、回表成本、排序 / 分组代价和执行计划。
- 深分页、函数操作索引列、隐式类型转换都是常见慢查询根因。
- SQL 优化必须结合系统上下文，不要只看语句本身。

## Summary

SQL 优化不是写法技巧竞赛，而是访问路径设计。真正成熟的工程师，不是只会改写 SQL，而是能从执行计划、索引结构和系统上下文一起判断这条查询为什么慢、该怎么改才值。
