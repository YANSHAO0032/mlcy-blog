# GC 调优入门：从现象、指标到调优动作的完整路径

## Problem

线上 Java 服务一旦出现下面这些现象，很多人第一反应就是“JVM 顶不住了”：

- 接口 RT 周期性抖高
- CPU 不算高，但服务偶发卡顿
- 堆内存明明很大，还是频繁 GC
- Full GC 一来，业务线程明显停顿
- Pod 没 OOM，但延迟越来越差

真正难的地方不在于会不会背 `-Xms`、`-Xmx`、`-XX:+UseG1GC`，而在于：

- 你能不能分清这是不是 GC 问题
- 你能不能判断是 Young GC 频繁、对象晋升过快，还是老年代压力异常
- 你能不能把“现象”还原成“对象生命周期和内存模型”的问题

GC 调优如果只停留在“参数大全”层面，基本很难在生产环境真正解决问题。

## Explanation

我理解 GC 调优，本质上是在回答三个问题：

1. 对象是怎么产生的
2. 对象为什么没有按预期被回收
3. 回收动作为什么影响了业务延迟或吞吐

所以调优的正确顺序通常不是先改 JVM 参数，而是先建立一条诊断路径：

```text
业务现象
-> GC 指标与日志
-> 对象分配与晋升模型
-> 找到根因
-> 选择调优动作
-> 验证效果
```

### 1. 先区分“是不是 GC 问题”

线上 RT 抖高不一定是 GC，也可能是：

- 数据库慢查询
- 下游 RPC 抖动
- 线程池打满
- 锁竞争严重
- 容器 CPU 被限流

所以第一步不要一上来就改 GC 参数，而是先看几个基础指标：

- JVM 堆使用率曲线
- Young GC / Old GC 次数和停顿时间
- Full GC 是否出现
- CPU 使用率和 system load
- 线程数、阻塞线程数
- 容器重启、内存限制和 OOM Kill 记录

如果你发现 RT 抖动时间点和 GC 停顿高度重合，再进入 GC 诊断会更稳。

### 2. 理解一条最基本的对象生命周期

大多数 Java 对象并不会长期存活，它们通常经历的是：

```text
Eden 分配
-> Minor GC
-> Survivor 复制
-> 晋升到 Old
-> 最终被回收
```

所以调优时要关注三个核心问题：

- 新生代对象是不是产生得过快
- 对象是不是过早晋升到老年代
- 老年代对象是不是没有被及时释放

很多 GC 问题，说到底不是“收集器不够强”，而是对象生命周期和业务代码模型不匹配。

### 3. 先看哪几类 GC

生产上至少要分清下面几种：

- `Minor GC`：主要回收新生代
- `Mixed GC`：G1 下同时回收部分老年代 Region
- `Full GC`：整个堆甚至包括元空间等一起参与回收，停顿通常最重

一个很常见的误区是：

```text
看到 GC 次数多，就以为 JVM 有问题。
```

其实不是。Young GC 多并不一定坏，关键要看：

- 单次停顿多久
- 回收后内存是否明显下降
- 老年代压力是否持续增长
- 是否影响业务 RT

如果 Young GC 很频繁，但每次只停几毫秒，而且整体吞吐稳定，这未必是问题。

### 4. 看 GC 日志时，重点不是“看懂参数”，而是看结构

一份 GC 日志真正有价值的信息，通常包括：

- 发生的是哪种 GC
- 停顿时间多长
- 回收前后堆占用变化
- 哪个分代或 Region 压力最大
- 是否发生晋升失败或并发失败

如果我在排查一份线上日志，通常会先问：

- Full GC 是不是偶发还是持续发生
- 每次 GC 后 Old 区有没有明显下降
- YGC 后对象是不是大量进入 Old
- GC 停顿尖刺和业务 RT 尖刺是否一致

如果 Old 区用量一路升高、Full GC 后也降不下来，优先怀疑：

- 内存泄漏
- 缓存对象长期持有
- 请求积压导致对象生命周期变长
- 大集合、大 Map 或批量对象没有及时释放

### 5. 常见线上问题，其实都能映射成几类对象模型问题

#### 5.1 Young GC 过于频繁

常见根因：

- 瞬时创建大量临时对象
- JSON 序列化 / 反序列化对象过多
- 日志拼接、字符串拷贝过多
- 批量查询一次性拉太多结果

这类问题很多时候优先改代码，而不是先动 JVM 参数。因为新生代再大，也只是延后回收时点。

#### 5.2 对象晋升过快

常见根因：

- Survivor 空间压力大
- 请求堆积导致对象“活得更久”
- 线程池排队过长
- 批处理任务把对象挂在内存里太久

这个问题在高并发业务里很常见。表面看像老年代不够，实际可能是链路变慢后，对象生命周期被拉长了。

#### 5.3 Full GC 频繁

常见根因：

- 老年代接近打满
- 显式调用 `System.gc()`
- 元空间不足
- G1 并发标记跟不上分配速度
- 大对象直接进入老年代

这时不要只盯着 Full GC 本身，更要看 Full GC 为什么被触发。

#### 5.4 Full GC 后内存仍降不下来

这个信号非常重要，通常意味着：

- 真正有强引用链在持有对象
- 某些缓存没有淘汰
- 静态集合长期堆积
- ThreadLocal 没清理
- MQ / 任务消费堆积导致对象链条延长

这时候继续调 GC 参数通常意义不大，更应该 dump 堆做对象分析。

### 6. 不同收集器关注点不同

#### 6.1 Serial / Parallel GC

- `Serial GC` 更简单，适合小堆、低并发环境
- `Parallel GC` 追求吞吐量，适合离线批处理、后台任务

如果业务目标是“单位时间处理更多任务”，Parallel GC 往往是合理选择。

#### 6.2 CMS

CMS 更早强调低停顿，但会带来碎片问题，而且已经逐渐退出主流。

现在更多是理解历史系统时会碰到 CMS，而不是新项目优先选它。

#### 6.3 G1

G1 是现在服务端比较常见的默认选择，优势是：

- 面向大堆
- 支持可预测停顿目标
- 不再严格按传统物理分代组织整个堆

但要注意，G1 不是“永远更快”，它只是更适合很多低停顿在线服务场景。

我的经验是：

- Web 服务、API 服务、交易后台服务：优先考虑 G1
- 纯离线批任务：Parallel GC 往往更简单直接

### 7. 调优时优先看哪些指标

如果要做一轮靠谱的 GC 调优，我通常会先盯这些指标：

- 每分钟 Young GC 次数
- 单次 Young GC 平均停顿和 P99 停顿
- Mixed / Full GC 次数
- Full GC 单次耗时
- Old 区回收前后占比
- 堆使用率 sawtooth 曲线是否正常
- GC 时间占总运行时间比例

比较好的堆曲线通常像锯齿：

- 内存上升
- GC 回落
- 再上升
- 再回落

如果一直只涨不怎么掉，就要小心老年代堆积或泄漏。

### 8. 调优动作，先改代码还是先改参数

我的原则比较明确：

#### 优先改代码的场景

- 大量无意义临时对象
- 大对象一次性分配
- 缓存缺少淘汰
- ThreadLocal、静态集合持有对象
- 线程池积压严重

#### 优先调 JVM 的场景

- 堆大小明显不合理
- 收集器和业务目标不匹配
- 新生代过小导致 Young GC 过于频繁
- G1 停顿目标需要结合业务延迟进一步调节

也就是说：

```text
参数调优解决的是“回收策略和内存布局问题”，
代码优化解决的是“对象模型和生命周期问题”。
```

后者通常更根本。

### 9. 一条比较实用的排查路径

如果线上服务出现疑似 GC 问题，我通常会这样走：

1. 先看监控，确认 RT 抖动和 GC 是否相关
2. 看 GC 日志，分清是 Young 压力、晋升压力还是 Full GC
3. 看 Old 区趋势，判断是否存在明显堆积
4. 看线程池、请求量、批任务、缓存命中，判断是不是业务模型引起
5. 必要时 dump 堆，定位大对象和引用链
6. 最后再决定是改代码、改参数，还是一起改

这个顺序的价值在于，能避免“把一切问题都归咎于 JVM”。

### 10. 在高并发业务里的几个真实关注点

如果是交易、行情、增长、钱包这类后端服务，GC 调优要特别关注：

- 大量 JSON 编解码产生的临时对象
- WebSocket 推送带来的消息堆积
- 批量风控计算导致的集合对象膨胀
- Kafka 消费堆积让对象在内存中停留过久
- 缓存和本地热点数据结构长期占用 Old 区

这种场景里，GC 问题经常不是单点参数问题，而是“系统吞吐、消费速度、对象滞留”共同作用的结果。

## Key Points

- GC 调优第一步不是改参数，而是确认问题是否真的来自 GC。
- 重点看对象分配、对象晋升和老年代回收效果。
- Young GC 多不一定坏，关键看停顿和业务影响。
- Full GC 后 Old 区降不下来，优先怀疑对象持有或内存泄漏。
- 代码优化解决对象生命周期问题，参数调优解决回收策略问题。
- 调优目标必须和业务目标绑定，是追求吞吐还是追求低停顿。

## Summary

GC 调优不是参数玄学，而是一门把“业务现象”映射到“对象生命周期和回收模型”的工程能力。真正成熟的做法，是先看监控和日志，再判断对象是怎么活下来的、为什么没被及时回收、为什么回收影响了业务。只有这样，JVM 调优才不是盲试，而是有路径、有证据、有验证的系统化工作。
