# 现货交易系统总览：负责人要治理的不是接口，而是一条业务价值链

## Problem

现货交易系统很容易被误解成“下单接口 + 撮合引擎 + 行情推送”。但站在负责人视角，真正要负责的是一条完整业务价值链：

```text
用户接入
-> 下单与撤单
-> 订单编排
-> 撮合路由
-> 成交回报
-> 账户资金
-> 行情推送
-> 风控限额
-> 运营配置
-> 对账补偿
```

任何一段边界不清楚，最后都会变成线上问题：订单状态不一致、资金流水解释不清、行情延迟、运营误配置、返佣重复、风控绕过，甚至资损。

所以现货负责人最重要的能力，不是只会看某个服务，而是能把主链路、旁路链路、资金链路和运营链路拆开治理。

## 核心分层

### 1. 接入层：接住请求，但不吞掉业务边界

接入层负责 App、Web、OpenAPI 等入口，核心职责是：

- 鉴权、签名、白名单和限流
- 参数标准化
- traceId / requestId 透传
- 重复请求识别
- 用户状态检查

这一层不应该承载复杂资金变更，也不应该直接操作撮合状态。它要做的是把外部请求变成系统内部可以判断、可以拒绝、可以追踪的标准输入。

### 2. 订单编排层：决定什么订单可以进入撮合世界

订单编排层通常处理：

- 交易对是否开放
- 买卖方向、价格、数量、精度是否合法
- 用户是否被冻结或受限
- 市价单、限价单、特殊来源订单如何处理
- 单日限额、持仓上限、价格保护、风控阈值
- 手续费和费率快照
- 资金冻结或预校验

它不负责“谁和谁成交”，但负责保证进入撮合的订单是安全、完整、可追踪的。

### 3. 撮合与路由层：保证确定性和低延迟

撮合层的关键不是写出一个 OrderBook，而是保证：

- 同一交易对的订单进入确定节点
- 输入顺序可控
- 撮合结果可解释
- 查询、撤单和成交回报使用同一套路由语义
- 节点异常时有明确恢复路径

在多撮合节点场景里，负责人要特别关注交易对和撮合集群的绑定关系，以及配置变更是否有审计和回滚能力。

### 4. 账户资金层：系统里最不能“差不多”的地方

现货交易完成后，真正的业务结果要落到账户资金上。资金层负责：

- 下单冻结
- 成交扣减冻结
- 对手方入账
- 手续费扣减
- 撤单解冻
- 流水和历史快照
- 对账和补偿

负责人必须把资金流水当成证据链，而不是日志。任何余额变化都要回答：由哪笔业务触发、前后余额是多少、是否重复执行、出问题能否恢复。

### 5. 行情与推送层：把成交事实变成用户可感知状态

行情系统不是简单 WebSocket 广播。它要把撮合结果转换成：

- trade stream
- ticker
- depth snapshot
- depth diff
- kline
- 用户级成交推送

行情链路要关注热点交易对隔离、慢连接治理、快照和增量配合、事件延迟监控，以及公共行情和私有用户事件的隔离。

### 6. 运营与增长层：依赖交易结果，但不要侵入主链路

上币、费率、VIP、平台币抵扣、返佣、活动、报表都属于业务增长能力。它们很重要，但不应该阻塞下单和撮合主链路。

更合理的方式是：

- 主链路输出标准交易结果
- 增长和统计消费结果事件
- 旁路失败可重试、可补偿、可审计

## 负责人检查清单

- 主链路和旁路链路是否分开：下单、撮合、资金不能被报表、通知、返佣拖慢。
- 交易对配置是否有发布、回滚、审计和白名单能力。
- 订单状态和资金状态是否分别建模，不能互相假设已经成功。
- 每笔资金变化是否有流水、快照、业务单号和幂等键。
- 撮合路由是否能解释：这笔订单为什么发到这个节点。
- 行情是否支持快照 + 增量，是否能发现版本不连续。
- 运营后台是否有权限控制和操作审计。
- 风控规则是否能在不改代码的情况下配置，但配置变更必须可追踪。
- 对账发现差异后是否有补偿路径，而不是直接改余额。

## Summary

现货交易系统不是几个接口的集合，而是一套低延迟、强一致、可审计、可运营的业务基础设施。负责人要做的不是把所有逻辑塞进一个大流程，而是把接入、订单、撮合、资金、行情、运营、风控和恢复拆成清晰边界，让每个问题都能定位、解释和修复。
