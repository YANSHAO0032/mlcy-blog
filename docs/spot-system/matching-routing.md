# 撮合路由与多节点治理：订单发到哪里，必须能解释

## Problem

撮合引擎追求低延迟和确定性，但在真实交易所系统里，撮合往往不是一个单节点服务。系统可能按交易对、市场、撮合集群或用户维度拆分节点。

这会带来一个负责人必须回答的问题：

```text
一笔订单为什么被发到这个撮合节点？
```

如果下单、查询、撤单、成交回报使用不同路由逻辑，就会出现：

- 订单发到 A 节点，撤单查到 B 节点
- 查询不到用户挂单
- 交易对切换撮合集群后历史状态混乱
- 配置变更不可追踪
- 节点异常时不知道哪些交易对受影响

## 路由模型

一个稳妥的撮合路由模型通常包含三层：

```text
交易对配置
-> 撮合集群配置
-> 节点选择规则
```

### 1. 交易对绑定撮合集群

交易对配置不仅是 `BTC-USDT` 是否开放，还应该能表达：

- base / quote
- symbol 状态
- 所属撮合 server 或 cluster
- 是否支持市价单
- 精度和最小数量
- 是否处于灰度或白名单阶段

撮合路由应从交易对配置获取所属集群，而不是在代码里写死。

### 2. 撮合集群配置要可发布、可审计

撮合集群配置通常类似：

```json
{
  "cluster1": ["http://match-1", "http://match-2"],
  "cluster2": ["http://match-3", "http://match-4"]
}
```

负责人要关注：

- 配置是否有版本
- 谁改了配置
- 什么时候生效
- 是否支持回滚
- 改动前后影响哪些交易对

撮合配置不是普通环境变量，它直接决定订单流向。

### 3. 节点选择要稳定

节点选择规则可以按用户 ID、订单 ID、交易对或分区键取模。关键是稳定：

- 下单、撤单、查询要使用一致规则
- 同一用户或同一订单相关操作能找到同一状态所在节点
- 节点扩缩容要有迁移策略

如果简单随机发请求，系统很快会失去状态一致性。

## 操作链路

### 下单

```text
tradeSymbol
-> 读取交易对配置
-> 获取 base / quote
-> 获取撮合集群
-> 选择节点
-> 发送创建订单命令
```

### 查询挂单

查询不能只查数据库，因为数据库可能是最终状态或异步落库结果。对于撮合内存中的活跃订单，应该通过同样路由访问对应节点。

### 撤单

撤单更依赖路由一致性：

```text
orderId / uid / symbol
-> 同样的交易对配置
-> 同样的撮合集群
-> 同样的节点选择规则
-> 发送撤单命令
```

撤单成功与否最终要以撮合回报为准。

## 风险点

- 交易对配置缓存未刷新，导致订单发到旧节点。
- 撮合集群配置手动修改，没有审计。
- 节点列表扩容后取模结果变化，历史订单找不到。
- 查询和撤单没有复用下单路由。
- 撮合节点异常时，没有交易对级别影响面清单。
- 路由失败后直接吞异常，订单进入未知状态。

## 治理建议

### 配置治理

- 交易对到撮合集群的绑定关系要有后台展示。
- 每次修改要记录操作人、时间、旧值、新值和生效范围。
- 新交易对上线先走灰度白名单。
- 撮合节点变更需要发布计划和回滚计划。

### 可观测性

每笔订单的关键日志应包含：

- symbol
- base / quote
- cluster
- node address
- route key
- order id
- request id

这样线上排查时可以直接判断订单被发到了哪里。

### 故障恢复

负责人要提前定义：

- 某个撮合节点不可用时，哪些交易对暂停。
- 是否允许自动切节点。
- 切节点前旧内存订单簿如何恢复。
- 未完成撤单和未成交订单如何处理。
- 行情和账户下游如何重新对齐。

## 负责人检查清单

- 下单、查询、撤单是否使用同一套路由语义。
- 交易对和撮合集群绑定是否可见、可审计、可回滚。
- 节点选择规则扩缩容时是否稳定。
- 路由失败是否会进入明确失败状态，而不是未知状态。
- 日志是否能回答“订单发到哪里”。
- 撮合节点异常时是否能列出受影响交易对。
- 切换撮合节点前是否有快照、回放或停盘策略。

## Summary

撮合路由的核心不是把 HTTP 请求发出去，而是让订单、查询、撤单和回报共享稳定的状态定位规则。负责人要确保每笔订单的流向可解释、配置可审计、故障影响面可评估、节点切换可恢复。
