# MySQL 锁与 MVCC：并发控制不是只有加锁，还有版本和可见性

## Problem

MySQL 并发问题经常会表现成这些现象：

- update 卡住很久
- 两条 SQL 谁也不返回
- 查询明明只是 select，却还是和写操作互相影响
- 业务说“数据被覆盖了”，但没有报错

如果只知道“数据库有锁”，通常很难真正解释这些问题。

## Explanation

我理解 MySQL 并发控制，要同时看两套机制：

- 锁：解决当前读下的互斥和顺序
- MVCC：解决快照读下的可见性和读写并发

也就是说：

```text
MySQL 并不是所有一致性都靠锁顶着，
很多读操作之所以能并发，是因为版本链和可见性规则在工作。
```

### 1. 常见锁类型，先从工程角度理解

在 InnoDB 里，经常会遇到：

- 行锁
- 间隙锁
- Next-Key Lock
- 意向锁

真正排障时，我最关注的是：

- 锁锁住的是哪一行
- 锁锁住的是某个区间，还是具体记录
- 为什么这条语句会升级成区间锁

### 2. 行锁不是“只要加 where id 就一定轻”

很多人会以为：

```sql
update table set ... where id = ?
```

一定只锁一行。

通常情况下是这样，但前提是：

- 命中了合适的索引
- 执行计划没有退化

如果条件没走索引，或者走了范围扫描，锁影响范围可能比想象中大得多。

所以数据库锁问题和索引问题往往是绑在一起的。

### 3. 间隙锁和 Next-Key Lock，是理解并发阻塞的重点

InnoDB 为了避免某些并发插入导致的不一致，会锁住“记录之间的区间”。

这就是为什么有时你明明没有锁到某一条具体记录，插入还是被挡住了。

很多“为什么插不进去”的问题，本质是：

- 事务 A 锁住了某个范围
- 事务 B 想往这个范围插入
- 被间隙锁或 Next-Key Lock 挡住

这类问题如果只从“谁锁了哪一行”去理解，通常会很困惑。

### 4. MVCC 让普通查询不必总是等写锁

MVCC 的价值就在于：

- 读不一定阻塞写
- 写也不一定阻塞普通快照读

它依赖的是：

- 隐藏版本字段
- undo log
- Read View

普通 `select` 读取的是对当前事务可见的历史版本，而不是永远读最新值。

这也是为什么：

- 事务里普通查询可能看不到别人的新提交
- 但当前读语句又能看到最新状态并参与加锁

### 5. 丢失更新问题，很多时候不是数据库自动帮你兜底

如果两个事务都这样做：

1. 先查当前值
2. 在应用层计算新值
3. 再 update 回去

那在没有额外控制时，就可能出现覆盖写。

常见解决方式有：

- `select ... for update`
- 乐观锁版本号
- 直接使用原子更新 SQL

也就是说，数据库锁不是“帮你自动保证所有业务一致性”，很多场景还是要业务自己表达并发控制策略。

### 6. 排查锁问题时，我通常先看三件事

1. 被阻塞的是哪条 SQL
2. 持锁的是哪条 SQL
3. 它们是不是命中了同一索引范围

如果只盯着“谁在等锁”，不去看索引和执行计划，往往只能看到表象。

### 7. 在交易和账户系统里，锁设计要非常克制

例如资金扣减、冻结、解冻这类链路里，最怕的不是“没加锁”，而是：

- 事务过大
- 持锁时间过长
- 热点账户竞争严重
- 锁顺序不一致导致死锁

所以更成熟的做法通常是：

- 缩小事务范围
- 保证固定的更新顺序
- 尽量用单行、定点、命中索引的更新
- 必要时做账户分片或异步串行化

## Key Points

- InnoDB 并发控制依赖“锁 + MVCC”两套机制，而不是单纯靠锁。
- 锁问题很多时候和索引设计直接相关。
- 间隙锁和 Next-Key Lock 是理解插入阻塞、范围竞争的关键。
- 普通快照读依赖 MVCC，不一定读取最新值。
- 丢失更新等问题往往还需要业务层显式表达并发控制策略。

## Summary

理解 MySQL 并发控制，不能只停留在“有行锁、有表锁”这种层面。真正重要的是看懂当前读、快照读、索引范围、版本链和锁冲突之间的关系。只有这样，线上那些 update 卡顿、插入阻塞、数据覆盖问题才真正可解释。
