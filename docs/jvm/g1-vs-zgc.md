# G1 与 ZGC 对比：工程在 JDK 21 下如何选择

G1 和 ZGC 都能在 JDK 21 中承担在线服务的垃圾回收工作，但它们解决问题的路径不同：G1 用 Region 和回收集合控制每次暂停的工作量，ZGC 则用着色指针、读屏障和并发重定位把大部分工作移出暂停阶段。

对交易系统，选型不能停留在“谁的停顿更短”。订单服务、RocketMQ 消费和 WebSocket 推送具有不同的对象生命周期、吞吐目标和故障模式，必须在相同资源约束和业务流量下比较尾延迟、吞吐、CPU、RSS 和积压。

文中的命令是 JDK 21 评估模板，不代表仓库当前已经统一启用对应收集器。

## 1. 架构对比

| 维度 | G1 | ZGC |
| --- | --- | --- |
| 核心目标 | 在吞吐和可预测停顿之间平衡 | 尽量缩短停顿，尤其是大堆场景 |
| 堆组织 | 等大小 Region，保留年轻代和老年代角色 | 分页式堆布局，以并发标记和重定位为核心 |
| 主要停顿 | Young GC、Remark、Cleanup、Mixed GC 中的复制工作 | 根处理和阶段切换等短暂停顿 |
| 标记 | 并发标记，Remark 修正引用变化 | 大部分并发标记 |
| 整理 | Evacuation 时复制 Region 中的存活对象 | 并发重定位，读屏障修正旧引用 |
| 屏障成本 | 写屏障、卡表和 Remembered Set | 读屏障、着色指针和重映射 |
| 停顿与堆大小 | 通过回收集合控制，但存活集和复制量仍影响停顿 | 停顿通常更少受堆大小影响 |
| CPU 成本 | 通常更偏向吞吐平衡 | 并发回收工作更多，需要 CPU 余量 |
| 调优复杂度 | 指标成熟，Region/Mixed GC 需要理解 | 参数较少，但资源预算和分配速率更关键 |
| 典型风险 | Mixed GC 跟不上、Humongous Object、Full GC | 分配速率过高、Allocation Stall、CPU/RSS 压力 |

## 2. 回收流程差异

### G1

```text
Young GC
-> 并发标记
-> Remark / Cleanup
-> 多轮 Mixed GC
-> 必要时 Full GC
```

G1 会预测每个 Region 的回收收益和成本，在 `MaxGCPauseMillis` 目标下选择回收集合。暂停阶段复制存活对象，因此暂停时间会受到存活集、跨 Region 引用和 CPU 的影响。

### ZGC

```text
Pause Mark Start
-> Concurrent Mark
-> Pause Mark End
-> Concurrent Prepare for Relocation
-> Concurrent Relocate
```

ZGC 让业务线程和重定位并发运行，并通过读屏障处理旧引用。它减少了集中复制带来的长暂停，但并发 GC 线程会持续消耗 CPU 和内存带宽。

## 3. 停顿、吞吐与资源成本

### 3.1 停顿

如果服务的核心目标是控制订单 P999 或避免 WebSocket 推送出现明显时间断层，ZGC 通常更值得进入候选集。但 G1 的实际停顿如果已经稳定低于业务容忍阈值，换成 ZGC 未必产生可感知收益。

### 3.2 吞吐

G1 的屏障和并发成本通常更偏向综合平衡。ZGC 为低停顿付出更多并发工作，CPU 紧张时可能降低业务吞吐。最终要比较单位 CPU 下的请求量、消息消费量和推送量，而不是只看 GC 日志。

### 3.3 堆和 RSS

两种收集器都需要为存活对象、突发分配和回收过程保留空间。容器内存必须覆盖：

```text
Java Heap
+ Metaspace
+ Thread Stack
+ Direct Buffer
+ JIT Code Cache
+ Native Library
+ GC Native Structures
```

`-Xmx` 等于容器 limit 是高风险配置。`ex-parent` 中存在较大的线程池和 Netty/WebSocket 网络缓冲，堆外预算尤其不能省略。

## 4. 按工程服务类型选择

### 4.1 普通 API 和订单服务

订单 API 有明显的短命对象分配，也关注请求尾延迟。

优先从 G1 开始的条件：

- 堆规模中等
- G1 P99/P999 停顿满足业务要求
- CPU 资源有限，更关心综合吞吐
- 团队已有成熟的 G1 日志和告警

优先评估 ZGC 的条件：

- G1 的长尾停顿与订单 RT 尖刺明确相关
- 增大 CPU 预算后仍有稳定收益
- 堆较大或存活对象较多
- 有可靠的同流量对照压测

### 4.2 RocketMQ 消费服务

消息消费首先是吞吐和积压问题。消费者速度不足时，换收集器不会自动消除积压。

建议：

- 先比较生产 TPS、消费 TPS、批次大小和线程池队列。
- 如果 G1 停顿导致周期性消费断层，再评估 ZGC。
- 如果 CPU 已接近 limit，优先处理业务耗时和线程池模型。
- 将重试、失败补偿和顺序消费的延迟一起纳入压测。

多数情况下，G1 是稳妥基线；只有停顿确实成为消费抖动来源时，ZGC 的低停顿价值才会显现。

### 4.3 WebSocket 推送服务

WebSocket 服务同时维护长寿命连接对象和高频短命消息对象，对尾延迟与堆外内存都敏感。

ZGC 的潜在优势：

- 减少长暂停造成的推送断层
- 在较大连接映射和存活集下保持较短停顿

必须额外验证：

- Netty Direct Buffer 和进程 RSS
- 慢客户端与发送队列上限
- 连接、认证和订阅映射的清理
- CPU 增加是否影响网络事件循环

如果推送抖动来自慢客户端或无界队列，G1/ZGC 都不是根治方案。

### 4.4 批处理和后台任务

批处理通常更重视吞吐。若任务允许较长暂停，G1 往往更直接；如果批处理与在线业务共进程并且会影响在线 P99，应先考虑拆分部署，再讨论收集器。

## 5. JDK 21 配置模板

### G1 基线

```bash
java \
  -Xms4g -Xmx4g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=100 \
  -Xlog:gc*,safepoint:file=/data/logs/g1-%t.log:time,uptime,level,tags:filecount=10,filesize=100M \
  -jar app.jar
```

### ZGC 基线

```bash
java \
  -Xms4g -Xmx4g \
  -XX:+UseZGC \
  -Xlog:gc*,safepoint:file=/data/logs/zgc-%t.log:time,uptime,level,tags:filecount=10,filesize=100M \
  -jar app.jar
```

对比时保持 JDK、构建产物、`-Xms/-Xmx`、容器 CPU/内存、流量和下游依赖一致。不要给 G1 4 核、给 ZGC 8 核后直接比较，也不要一边改变堆大小一边改变收集器。

## 6. 压测矩阵

| 变量 | 建议分组 | 观察结果 |
| --- | --- | --- |
| 流量 | 稳态、两倍突发、阶梯升压 | P50/P99/P999、吞吐、错误率 |
| 订单对象 | 普通订单、大批量请求、复杂校验 | 分配速率、Young 周期、CPU |
| RocketMQ | 正常消费、生产突增、消费者降速 | 积压、消费延迟、线程池队列 |
| WebSocket | 基线连接、连接翻倍、慢客户端 | 推送延迟、队列、Direct Buffer、RSS |
| 堆大小 | 2 GB、4 GB、8 GB 等固定组 | 回收周期、停顿、内存余量 |
| CPU limit | 低、中、高三档 | GC 与业务 CPU、throttling |
| 故障 | 下游慢、数据库慢、消息重试 | 对象滞留、Old/存活集、恢复时间 |

每组至少包含预热期、稳定采样期和突发期。只跑几分钟通常不足以观察并发标记、Mixed GC、连接增长和消息积压。

## 7. 必须同时记录的指标

### 业务结果

- API 和订单处理 P50/P99/P999
- 请求吞吐、错误率和超时率
- RocketMQ 消费 TPS、积压量和重试数量
- WebSocket 推送延迟、成功率和连接数

### JVM 结果

- GC 暂停平均值、P99 和最大值
- G1 Young/Mixed/Full GC 次数和原因
- ZGC 周期时间、分配受阻和堆水位
- 每秒对象分配量和存活集大小
- GC CPU 占比、总 CPU、RSS 和 Direct Buffer

最终结论至少要回答：尾延迟是否下降、吞吐是否保持、CPU 是否可接受、内存是否有余量、故障流量下是否能够恢复。

## 8. 常见故障如何判断

### 8.1 Young GC 频繁

G1 下先看单次停顿和分配速率；如果停顿短且业务稳定，不必仅为降低次数调参。ZGC 下则重点看回收周期和分配速度，不再用 Young GC 次数作为核心信号。

### 8.2 G1 Mixed GC 跟不上

检查并发标记是否启动过晚、CPU 是否不足、存活对象是否过多，以及 Humongous Object 是否持续增加。可以评估 ZGC，但要先排除缓存、队列和泄漏问题。

### 8.3 ZGC 分配受阻

说明分配线程正在等待可用空间。优先检查分配速率、堆余量、GC CPU 和容器限流，而不是继续追求更低停顿。

### 8.4 进程被容器杀死

如果 Java Heap 尚未到 `-Xmx`，进程仍可能因为 RSS 超过容器 limit 被杀。检查 Direct Buffer、线程数、Metaspace、JIT 和 native memory；更换收集器不能替代完整的内存预算。

### 8.5 Full GC 后内存仍然很高

这通常指向长寿命引用、缓存、订阅映射、无界队列或泄漏。应使用 Heap dump 和引用链分析，不要把问题包装成 G1 与 ZGC 的选型争论。

## 9. 决策表

| 场景 | 建议 |
| --- | --- |
| G1 已满足 P99/P999，CPU 和吞吐稳定 | 保持 G1，避免无收益切换 |
| G1 长尾停顿与订单 RT 明确相关 | 同资源压测 ZGC |
| 大堆、高存活集、尾延迟要求严格 | 优先把 ZGC 纳入候选 |
| CPU 紧张、吞吐优先 | 优先验证 G1 |
| MQ 积压来自业务处理慢 | 先修消费链路，不靠更换 GC |
| WebSocket 抖动来自慢客户端和队列 | 先治理背压和连接清理 |
| RSS 接近容器 limit | 先做堆内外内存预算 |
| Full GC 后对象仍无法释放 | 先定位引用链和泄漏 |

## 10. 推荐落地顺序

1. 使用 JDK 21 固定构建产物和运行资源。
2. 以 G1 建立业务与 GC 指标基线。
3. 证明尾延迟问题与 G1 停顿确实相关。
4. 用相同堆、CPU 和流量运行 ZGC 对照组。
5. 覆盖订单突增、消息积压和慢客户端等故障场景。
6. 根据 P99/P999、吞吐、CPU、RSS 和恢复时间决策。
7. 灰度上线，并保留快速回退参数和告警阈值。

## 总结

G1 更像是在可预测停顿和吞吐之间寻找平衡，ZGC 则把低停顿放在更高优先级，并用并发 CPU 和屏障成本换取更短暂停。对工程来说，G1 适合作为稳定基线，ZGC 适合作为订单长尾延迟、大堆或 WebSocket 推送停顿问题的重点候选。最终选择必须由同构压测和业务指标决定，而不是由收集器名称决定。
