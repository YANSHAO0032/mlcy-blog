# MySQL 事务与隔离级别：一致性不是概念题，而是并发下的行为边界

## Problem

很多人能背出四种隔离级别，但线上真遇到问题时，还是会搞不清：

- 为什么同一事务里两次查询结果不一样
- 为什么明明加了事务，还是会出现并发覆盖
- 为什么有时查不到别人的提交，有时又能查到
- 为什么锁冲突看起来和“隔离级别”有关

这说明事务和隔离级别如果只停留在定义层面，实际工程里很难真正用好。

## Explanation

我理解事务隔离级别，重点不是定义本身，而是：

```text
数据库在并发读写时，允许你看到什么，不允许你看到什么。
```

隔离级别解决的核心问题，是并发下的数据可见性和一致性边界。

### 1. 事务四大特性，最难的其实是 I

ACID 里真正最容易在业务里出问题的是 Isolation，也就是隔离性。

因为：

- 原子性更多是数据库机制兜底
- 持久性更多是日志机制兜底
- 一致性最终要靠业务约束和事务边界配合
- 隔离性则直接决定并发操作下你“看到的世界”

### 2. 四种隔离级别，本质是并发可见性的不同取舍

#### Read Uncommitted

可能读到未提交数据，几乎不会在严肃业务中采用。

#### Read Committed

只能读到已提交数据，但同一事务里两次读可能不一样，容易出现不可重复读。

#### Repeatable Read

MySQL InnoDB 默认隔离级别。它通过 MVCC 让同一事务中的快照读保持一致，减少不可重复读问题。

#### Serializable

隔离最强，但并发能力最差，很多操作会退化成串行执行。

### 3. 不要把“当前读”和“快照读”混为一谈

这是理解 InnoDB 的关键。

- 普通 `select` 多数是快照读
- `select ... for update`
- `select ... lock in share mode`
- `update / delete / insert`

这些更偏向当前读，它们会读取最新版本并参与锁竞争。

所以很多“为什么我事务里看到的数据不一样”的问题，其实是：

- 第一次是快照读
- 第二次是当前读

这两种行为语义本来就不同。

### 4. MySQL 默认的 Repeatable Read 为什么还能防部分幻读

从教材定义看，Repeatable Read 主要解决不可重复读，幻读通常要更高隔离级别才能彻底避免。

但 InnoDB 通过：

- MVCC
- Next-Key Lock

在很多当前读场景下也能抑制幻读问题。

所以实际工程里不要只按数据库教材理解 MySQL，而要按 InnoDB 的具体实现去理解。

### 5. 事务隔离级别从来不是越高越好

隔离越强，通常意味着：

- 锁冲突更多
- 并发吞吐更低
- 延迟更高

所以选隔离级别时，应该先问：

- 这个业务更怕脏读，还是更怕吞吐下降
- 是资金类强一致链路，还是后台查询链路
- 是否可以接受通过幂等、版本号、补偿等方式降低数据库隔离压力

### 6. 在业务工程里，更常见的问题不是“隔离级别选错”，而是边界没设计好

例如：

- 一个大事务里做太多操作
- 同一事务里混合快照读和当前读却没意识到差异
- 依赖“先查后改”但没有版本控制或锁
- 后台批处理和在线写入争同一批数据

这些问题往往比单纯“隔离级别知识点”更容易造成事故。

## Key Points

- 隔离级别本质上是在定义并发读写时的数据可见性边界。
- InnoDB 默认是 `Repeatable Read`，但实际行为要结合 MVCC 和当前读一起理解。
- 快照读和当前读语义不同，很多并发问题都出在这里。
- 隔离级别不是越高越好，要结合吞吐、延迟和一致性目标取舍。
- 实际项目里更重要的是事务边界和并发更新策略设计。

## Summary

事务隔离级别不是面试概念题，而是并发行为设计题。只有把快照读、当前读、MVCC 和事务边界一起理解，才能真正看懂线上那些“为什么这次查出来和上次不一样”的问题。
