# MySQL 索引设计：不是会建索引，而是会为查询路径建索引

## Problem

同一张表数据量上来之后，为什么有的查询依然很快，而有的 SQL 会突然变慢？为什么有时明明“已经建了索引”，执行计划还是不走索引，甚至比全表扫描还差？

## Explanation

我理解 MySQL 索引设计，关键不是背“最左前缀”“覆盖索引”这些口诀，而是把它看成一件和查询路径、数据分布、回表成本、写入成本强相关的工程设计。

索引本质上是在存储层维护一套有序数据结构。InnoDB 的聚簇索引和二级索引默认都基于 B+ 树，这意味着它天然擅长：

- 等值查询
- 范围查询
- 排序
- 前缀匹配

但它并不天然擅长：

- 任意模糊匹配
- 大量离散条件
- 没有过滤性的低选择度字段

所以索引设计的第一原则不是“给查询字段都建上索引”，而是：

```text
围绕高频查询路径，设计能降低扫描行数、减少回表、兼顾写入成本的索引。
```

### 1. 先理解 InnoDB 里的两类索引

#### 1.1 聚簇索引

InnoDB 的主键索引就是聚簇索引，叶子节点直接存整行数据。

这意味着：

- 主键查询通常很快
- 表数据物理上按主键组织
- 主键过大，会让所有二级索引变胖

因为二级索引的叶子节点里存的不是整行，而是：

```text
二级索引键 + 主键值
```

所以主键设计不只是表设计问题，也直接影响所有二级索引的体积和回表成本。

#### 1.2 二级索引

二级索引叶子节点不会存整行数据，而是存索引列和主键值。查到后如果还需要其他字段，就必须回到聚簇索引再查一次，这就是回表。

这也是为什么：

- 覆盖索引通常更快
- `select *` 往往不利于索引优化

### 2. 联合索引最重要的不是“联合”，而是“顺序”

联合索引的本质不是把多个字段拼在一起，而是建立一个有序的多列查找路径。例如：

```sql
idx_user_status_created_at (user_id, status, created_at)
```

这个索引真正表达的是：

1. 先按 `user_id` 定位
2. 再在同一用户范围内按 `status` 过滤
3. 再按 `created_at` 做范围或排序

所以索引顺序设计要围绕实际查询条件：

- 高频等值条件优先
- 过滤性高的列优先
- 排序列尽量放在过滤列后面
- 范围条件后面的列，往往很难继续充分利用索引

### 3. 最左前缀原则，要理解成“有序路径是否还能继续走”

所谓最左前缀，不是死记硬背规则，而是理解：

```text
B+ 树只能按照建索引时的列顺序继续往下缩小范围。
```

例如联合索引：

```sql
(a, b, c)
```

这些查询通常可以较好利用索引：

- `where a = ?`
- `where a = ? and b = ?`
- `where a = ? and b = ? and c = ?`
- `where a = ? and b > ?`

但这些就容易打折甚至失效：

- `where b = ?`
- `where c = ?`
- `where a > ? and b = ? and c = ?`

因为路径在 `a` 这一层没对齐，或者在范围条件处已经被截断了。

### 4. 覆盖索引的价值，不只是“快”，而是“少一次主键树访问”

如果一个查询所需字段都能从二级索引叶子节点拿到，就不需要回表。

例如：

```sql
select user_id, status
from orders
where user_id = ? and status = ?;
```

如果索引正好是：

```sql
(user_id, status)
```

那这条查询就可能直接在索引层完成。

覆盖索引在高频读场景里非常值钱，尤其是：

- 列表页
- 后台分页
- 状态查询
- 统计前置过滤

但也不要为了“覆盖一切”把索引做得过宽，否则会带来：

- 索引体积变大
- 缓存命中率下降
- 写入维护成本上升

### 5. 索引不是越多越好，它是写入成本和读取收益的权衡

每多一个索引，都意味着：

- insert 要多维护一棵树
- update 如果改到索引列，会产生更多页变更
- delete 也要同步删除索引项
- Buffer Pool 要为更多索引页留空间

所以在写多读多的系统里，我更倾向于问这几个问题：

- 这个索引服务的是不是高频关键查询
- 它能不能被现有联合索引复用
- 这个查询有没有更好的改写方式
- 这条索引是否只是“为了以防万一”

“为所有可能查询都建索引”，最后通常会变成一个谁都不敢删、谁也解释不清的索引垃圾场。

### 6. 为什么建了索引，优化器还是可能不用

常见原因有：

- 扫描行数太多，优化器觉得还不如全表扫
- 条件选择度太差，比如状态字段只有 0/1
- 发生了隐式类型转换
- 对索引列做了函数操作
- 联合索引顺序和查询条件不匹配
- 回表成本过高

几个典型反例：

```sql
where phone = 13800138000
```

如果 `phone` 是字符串列，却按数字写，可能触发隐式转换。

```sql
where date(create_time) = '2026-05-12'
```

对索引列套函数，索引通常难以高效利用。

更好的写法通常是：

```sql
where create_time >= '2026-05-12 00:00:00'
  and create_time <  '2026-05-13 00:00:00'
```

### 7. `EXPLAIN` 的重点不是会用，而是知道看什么

我看执行计划时，通常优先关注这些字段：

- `type`
- `key`
- `rows`
- `filtered`
- `Extra`

尤其是：

- `type=ALL`：通常意味着全表扫描
- `Using filesort`：排序没在索引上完成
- `Using temporary`：可能有额外临时表开销
- `Using index`：通常说明覆盖索引

真正有价值的问题不是“它用了哪个索引”，而是：

- 扫描行数是不是被有效压下来了
- 排序和过滤是不是在索引层完成了
- 是否存在大量回表

### 8. 分页 SQL 的索引设计最容易踩坑

例如后台经常会写：

```sql
select *
from orders
where status = 1
order by id desc
limit 100000, 20;
```

这类深分页即使有索引，也可能很慢，因为要跳过大量行。

更好的思路通常是：

- 用上次分页最后一个 id 做游标翻页
- 先走覆盖索引拿主键，再回表取详情
- 避免无意义的超深 offset

### 9. 在业务系统里，索引设计要贴着查询模型走

比如交易系统常见查询：

- 按 `user_id + status + created_at` 查订单列表
- 按 `symbol + created_at` 查成交记录
- 按 `account_id + asset` 查账户余额

这类索引设计，不能只看单列含义，而要看：

- 谁是最稳定的过滤条件
- 谁承担排序
- 谁决定回表量
- 查询是否会长期演化

例如一个“用户订单列表”场景，往往更合理的是：

```sql
(user_id, status, created_at)
```

而不是单独建：

- `(user_id)`
- `(status)`
- `(created_at)`

后者看起来多，实际上未必更有效。

### 10. 我的索引设计习惯

如果是做一张新表，我通常会按下面的顺序思考：

1. 这张表最核心的 3 到 5 条查询是什么
2. 哪些查询是分页列表，哪些是点查，哪些是范围查
3. 哪些字段过滤性高，哪些字段只是辅助排序
4. 是否可以通过联合索引覆盖多个查询
5. 写入量有多大，索引维护成本是否能接受

索引不是 schema 收尾动作，而应该在建模阶段就跟着查询路径一起设计。

## Key Points

- InnoDB 聚簇索引叶子节点存整行，二级索引叶子节点存主键值，很多性能问题都和回表有关。
- 联合索引真正关键的是列顺序，而不是简单“把多个字段拼起来”。
- 最左前缀原则本质上是 B+ 树路径是否还能继续收缩。
- 覆盖索引可以显著减少回表，但过宽索引也会带来维护成本。
- 索引不是越多越好，必须同时考虑写入、空间和缓存命中成本。
- `EXPLAIN` 的重点是扫描行数、排序方式、回表成本，而不是只看是否“命中了索引”。

## Summary

好的索引设计，不是把所有字段都建上索引，而是围绕高频查询路径，设计出能减少扫描、控制回表、兼顾写入成本的访问结构。理解聚簇索引、联合索引、最左前缀和执行计划之后，你会发现真正的优化重点不是“索引技巧”，而是“查询模型是否合理”。
