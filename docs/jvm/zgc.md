# ZGC 垃圾收集器：JDK 21 下的低停顿实践

ZGC 面向的是另一类问题：当服务拥有较大堆、对象分配速率高，或者业务对 P99/P999 延迟非常敏感时，如何把垃圾回收停顿控制在很短范围内。它通过着色指针、读屏障和并发标记/重定位，把绝大部分回收工作放到业务线程运行期间完成。

这篇文章以 JDK 21 构建环境为基线，结合订单、RocketMQ 消费和 WebSocket 推送场景说明 ZGC 的工作方式、参数和运维边界。文中的配置是 JDK 21 的压测和生产评估模板，不代表仓库当前已统一启用 ZGC。

## 1. 为什么考虑 ZGC

在线交易和推送服务通常同时追求：

- API 和订单链路的低尾延迟
- 消息消费延迟可控
- WebSocket 推送不因长暂停出现明显断层
- 在较大堆下保持稳定吞吐

G1 通过 Region 和增量回收努力控制停顿，ZGC 则进一步把标记、转移和重定位设计成并发阶段，目标是让停顿时间尽可能与堆大小解耦。

但“低停顿”不等于“免费”。ZGC 仍然需要：

- 更多并发 GC 线程
- 读屏障和指针处理的 CPU 成本
- 足够大的堆空间承接分配速度
- 足够快的回收周期，避免分配线程耗尽可用内存

如果 CPU 已经被限流、对象分配率持续超过回收能力，ZGC 也可能出现分配阻塞、吞吐下降甚至 OOM。

## 2. ZGC 的核心结构

### 2.1 着色指针

ZGC 会利用对象引用指针中的元数据位记录对象状态，例如对象是否被标记、是否需要重映射。业务代码看到的仍然是普通 Java 引用，但 JVM 可以通过这些标记判断引用是否处在当前回收周期的正确状态。

着色指针让对象状态和引用本身关联起来，避免为每个对象维护一套完全独立的状态结构。它是 ZGC 能够在并发阶段处理引用变化的重要基础。

### 2.2 读屏障

在并发重定位期间，一个对象可能已经搬到新地址，但业务线程仍然持有旧引用。读屏障会在读取引用时检查对象状态，必要时把旧地址映射到新地址，保证业务线程继续使用有效对象。

读屏障的代价是业务线程读取对象引用时增加了额外指令和分支。大多数场景下代价可接受，但在极端高频对象访问、CPU 紧张或缓存命中很高的服务中，仍然需要通过压测验证吞吐变化。

### 2.3 并发标记和重定位

ZGC 的回收流程可以简化为：

```text
Pause Mark Start
-> Concurrent Mark
-> Pause Mark End
-> Concurrent Prepare for Relocation
-> Concurrent Relocate
```

不同 JDK 21 构建和日志配置下阶段名称可能有细节差异，但核心特征不变：短暂的根处理停顿之后，大部分标记和重定位与业务线程并发执行。

重定位完成后，旧引用不会要求应用立刻全部改写；读屏障和重映射表负责让旧引用逐步收敛到新地址。这种设计避免了传统整理过程把大量对象复制工作集中到一次长暂停中。

## 3. ZGC 的停顿模型

ZGC 的停顿主要集中在根集合处理和少量阶段切换，通常不会因为堆从几十 GB 增长到更大规模就线性增加。它更适合以下目标：

- 对尾延迟比平均吞吐更敏感
- 堆较大且存活对象较多
- 业务不能接受长时间 Stop-The-World
- 能够提供额外 CPU 给并发回收线程

但停顿短不表示业务延迟一定低。以下因素仍可能造成 P99 抖动：

- ZGC 并发线程与业务线程争用 CPU
- 容器 CPU limit 过低，GC 线程无法及时完成周期
- 分配速率超过回收速率，触发分配阻塞
- 线程池排队、下游 RPC 或数据库本身变慢
- Direct Buffer、线程栈、Metaspace 等堆外内存耗尽

所以 ZGC 评估必须同时观察 GC 停顿、应用吞吐、CPU、RSS 和业务延迟。

## 4. JDK 21 的评估配置

下面是一个适合作为基线的 ZGC 配置模板：

```bash
java \
  -Xms4g -Xmx4g \
  -XX:+UseZGC \
  -Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=100M \
  -jar exchange-app-api.jar
```

配置原则：

- `-Xms` 和 `-Xmx` 固定后，更容易比较两种收集器的行为。
- `-XX:+UseZGC` 明确选择 ZGC，压测时不要同时混用其他收集器选择参数。
- `-Xlog:gc*` 记录回收阶段、堆水位和并发周期，生产上应限制文件数量和单文件大小。
- 堆大小必须从容器内存预算倒推，不能把容器 limit 全部给 Java Heap。

### 4.1 `SoftMaxHeapSize`

JDK 21 可以使用：

```bash
-XX:SoftMaxHeapSize=3g
```

它表示 ZGC 尽量把堆使用控制在软上限附近，但在需要时仍可使用到 `-Xmx`。软上限不是硬内存隔离，也不是泄漏修复工具。

适合把软上限用于：

- 给堆设置一个常态工作水位
- 为突发流量保留一定弹性
- 观察达到软上限后回收频率和吞吐变化

不适合把软上限当作：

- 容器内存 limit 的替代品
- 防止所有 OOM 的保证
- 不经压测就直接套用的固定值

## 5. ZGC 与 ex-parent 的对象模型

### 5.1 订单 API

订单处理链路会产生请求对象、校验对象、数据库映射、消息体和日志参数。ZGC 可以降低回收停顿对订单 RT 的影响，但不能减少这些对象本身的分配量。

如果每个请求产生大量临时对象，ZGC 会投入更多并发 CPU 去追赶分配速率。优化 JSON 编解码、减少无效复制、控制批量结果，往往比单纯把堆调大更有效。

### 5.2 RocketMQ 消费

订单结果、成交结果和推送消息经过 RocketMQ 消费后，会进入反序列化、业务处理和发送流程。消费端线程池如果排队，消息对象和中间结果会在堆中停留更久。

ZGC 能降低“回收动作导致的长暂停”，但不能解决消费速度低于生产速度的问题。需要同时看：

- 消费 TPS 与生产 TPS
- 拉取批次大小
- 线程池队列长度
- 重试和补偿任务数量
- GC 周期内的分配速率和堆水位

### 5.3 WebSocket 推送

WebSocket 服务的连接、订阅关系、认证信息和心跳状态通常是长寿命对象；推送消息、JSON 字符串和网络缓冲则是短寿命对象。

如果慢客户端导致发送队列长期增长，ZGC 只会更平滑地回收不断产生的对象，却不会让队列自动消失。应先做慢客户端隔离、队列上限、丢弃策略和订阅清理，再比较 ZGC 与 G1 的尾延迟。

## 6. 分配速率比 GC 次数更重要

对 ZGC 来说，下面这个关系非常关键：

```text
对象分配速率 > 回收速率
-> 可用空间持续下降
-> 并发回收加速
-> 分配线程等待或触发更强的回收压力
```

因此建议按时间窗口观察：

- 每秒分配量
- 每秒回收量
- 堆已使用、堆容量和可用空间
- ZGC 周期持续时间
- 并发 GC 线程 CPU 占用
- Allocation Stall 或类似分配受阻信号

如果停顿指标很好，但分配受阻频繁，说明系统的真正瓶颈是回收速度、堆容量或 CPU 资源，而不是 Stop-The-World 停顿。

## 7. 日志和监控

### 7.1 GC 日志

JDK 21 推荐通过统一日志查看：

```bash
-Xlog:gc*,safepoint:file=/data/logs/gc-%t.log:time,uptime,level,tags
```

重点关注：

- Pause Mark Start/End 等停顿阶段的耗时
- Concurrent Mark 和 Relocate 的持续时间
- 堆使用量、回收前后水位和可用空间
- 是否出现分配受阻或回收周期追不上分配
- GC 线程数量和 CPU 消耗

### 7.2 JVM 与容器指标

- API、订单和 WebSocket 的 P99/P999
- RocketMQ 消费延迟、积压和重试数量
- 堆内存、RSS、Direct Buffer、线程数和 Metaspace
- CPU 使用率、CPU throttling 和 load
- Full restart、OOM Kill 和健康检查失败

ZGC 监控不能只展示“GC pause 很小”。如果 RSS 接近容器 limit，或者 CPU throttling 持续增加，服务依然可能不稳定。

## 8. 什么时候 ZGC 值得尝试

适合重点评估 ZGC 的情况：

- 订单或 API 的 P99/P999 对长暂停很敏感
- 堆容量较大，G1 Mixed GC 仍然出现明显尾延迟
- 存活对象较多，传统整理停顿成本较高
- 有足够 CPU 余量承担并发回收
- 能够通过压测复现真实流量和对象分配模型

不应直接选择 ZGC 的情况：

- 服务 CPU 已经接近 limit，没有并发 GC 余量
- 问题根因是数据库、RPC、线程池或消息积压
- 堆泄漏、缓存无限增长、队列无界等问题尚未修复
- 只有平均延迟，没有 P99/P999 和 GC 日志可对比

## 9. ZGC 实验方案

建议用同一份构建产物和同一套业务流量，对 G1 和 ZGC 做对照：

1. 固定 JDK 21、容器 CPU limit、内存 limit 和 `-Xmx`。
2. 固定订单请求分布、RocketMQ 消息速率和 WebSocket 连接数。
3. 分别记录 30 分钟稳定流量和 10 分钟突发流量。
4. 对比 P50/P99/P999、吞吐、GC 时间、CPU、RSS 和消息积压。
5. 增加慢客户端、消费者降速和批量突增等异常场景。
6. 观察是否出现分配受阻、容器内存逼近 limit 或线程池排队。

不要只在空载下比较暂停时间，也不要只用平均值证明收集器更好。

## 10. 常见误区

### 误区一：ZGC 没有停顿

正确说法是 ZGC 把绝大部分工作并发化，停顿很短，但仍存在短暂停顿和业务线程与 GC 线程的资源竞争。

### 误区二：ZGC 可以解决内存泄漏

收集器只能回收不可达对象。如果缓存、静态集合、订阅映射或队列仍然持有引用，ZGC 也不会释放它们。

### 误区三：堆越大越稳定

堆变大可以提供更多缓冲，但也可能掩盖泄漏、增加 RSS 风险，并让故障恢复成本变高。堆大小必须和存活集、分配速率、容器资源相匹配。

### 误区四：只看 GC pause

ZGC 的收益应该体现在业务 P99/P999 和稳定性上。如果 pause 很小但吞吐下降、CPU 打满或消息积压增加，就不能算成功。

## 11. ZGC 评估清单

1. 确认服务运行在 JDK 21，并记录实际 JVM 参数。
2. 打开 `gc*`、safepoint 和容器资源监控。
3. 固定 `-Xms`、`-Xmx`、CPU limit 和流量模型。
4. 记录分配速率、回收速率和分配受阻信号。
5. 将订单 RT、MQ 积压和 WebSocket 推送质量纳入结果。
6. 检查堆外内存和 RSS，防止只看 Java Heap。
7. 通过稳定流量、突发流量和故障流量三组场景做结论。

## 总结

ZGC 的核心价值是把大部分标记和重定位工作放到并发阶段，从而降低大堆和高存活集场景下的停顿风险。对于交易系统，它是否值得采用，取决于订单尾延迟、消息消费积压、WebSocket 推送质量和 CPU/RSS 成本的综合结果。低停顿只是目标之一，真正的生产结论必须来自同流量、同资源约束下的对照压测。
